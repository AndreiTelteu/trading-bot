# Design proposal: selected zero-volume execution bar

Status: **design only; economic-policy decision required before implementation**. Reviewed at `5e51cec`. No dataset repair, strategy tuning, code, or database change is proposed here.

## Evidence and boundary

Binance Spot [`GET /api/v3/klines`](https://api.binance.com/api/v3/klines?symbol=AVAXUSDT&interval=1m&startTime=1771041480000&limit=6) returns AVAXUSDT 1m at **2026-02-14 04:00:00 UTC** (open time `1771041600000`): OHLC `9.20000000`, base volume `0.00000000`, quote volume `0.00000000`, **0 trades**, close time `04:00:59.999`. At 03:59 it reports 1.09 base volume/1 trade; at 04:01, 4.60/2. The [official daily spot archive](https://data.binance.vision/data/spot/daily/klines/AVAXUSDT/1m/AVAXUSDT-1m-2026-02-14.zip) has 1,440 rows and the same values (archive timestamps are microseconds). Its [published CHECKSUM](https://data.binance.vision/data/spot/daily/klines/AVAXUSDT/1m/AVAXUSDT-1m-2026-02-14.zip.CHECKSUM) equals the downloaded ZIP SHA-256, `f0bc67baba2623010c9e48f052f717f252c9fba2cc9f57d07b2dd3cda42cac7f`. Binance's [public-data schema](https://github.com/binance/binance-public-data/blob/master/README.md) identifies fields 5/8 as volume/trades and documents the microsecond archive format and checksums. This establishes no **reported executions in that completed minute**, not the absence of order-book liquidity or the counterfactual outcome of our order. It is a valid observed bar; deleting it, changing its volume, or skipping the decision would falsify the immutable dataset.

The bar's final volume is knowable only **after** the minute closes. Strategy and risk at the preceding signal time must never see it. Using completed volume to judge simulated execution in that selected interval is ex-post execution evidence, not a contemporaneous pre-trade gate. The current OHLCV full-fill at next open for any positive-volume minute is already an optimistic model; this proposal adds only the certain no-reported-trade case and makes no claim about queue position, open-price availability, or order-book depth. A literal instantaneous IOC at the 04:00 open cannot infer its fate from the minute's final volume, so “IOC-like” below means a **one-window, zero-fill-and-cancel simulation**.

## Current path and failure

`RunStage05Comparison` runs cash, benchmark hold/trend, universe baselines, candidate and sensitivity rows on common assumptions. `runStage05StrategyWithPlanner` gets a plan at a completed reference bar, selects the immediate next execution timestamp and open with `nextFillPrices`, then calls `rebalanceStage05` or `executeStage06RiskStops`. Reductions precede additions; each group has deterministic symbol order. `runStage05Target` currently checks `intendedFillLiquidityError` **before** constructing the shared `DecisionContext` and running strategy → `PortfolioRiskEngine` → `BacktestBroker` → ledger/observer. Under `backtest-execution-v2` a selected zero-volume bar is a fatal `DiagnosticExecutionLiquidity`; v1 silently fills it. The common broker contract already supports a complete batch with `OrderRejection`, and the orchestrator observes broker rejections and records only economic fills. Stage 05 then checks approved/filled quantities and normally turns a zero fill into `DiagnosticAllocationRejected`. An adapter-level rejection alone will therefore not make the run continue.

The loop currently sets `lastTargets` after execution and `lastRebalance = signalAt` for non-stop plans, even if some target fails. Those fields are **decision cadence/selected targets**, not achieved holdings; changing them on a no-fill would create an unscheduled retry or rerank. Actual portfolio positions and cash already flow back to the next planner context. `finalLiquidationPrices` picks the last eligible selected bar; `liquidateStage05` uses the same per-symbol shared path. `mark_to_market` simply values remaining inventory at the last causal end mark. Stage 06's target/achieved-exposure assertions and mandatory-reduction handling can currently turn a failed exit into a fatal error; they need an explicit exception only for the new no-trade outcome, never for arbitrary risk, constraints, broker faults, or partial fills.

## Recommended new policy: `backtest-execution-v3` (decision requested)

1. Keep v1/v2 replay semantics immutable; select v3 explicitly for new jobs and bind its version, no-fill reason, timing/window rule, and unchanged cost model into every manifest/comparison/fold digest. Preserve the dataset manifest ID and all observed bars. No fallback to a later nonzero-volume bar and no use of its price for this intent.
2. At the original signal, form the same target intent and run the **same strategy and risk engine** with causal marks. For an approved intent whose exact selected execution bar is present, finite, and has zero reported base volume **and zero trades when that field exists**, have the **backtest simulation broker** return a complete, terminal *simulated zero-fill/cancel* outcome with a code such as `simulated_no_fill_zero_trades`, evaluated at that window's end and correlated to intent/order ID, selected bar timestamp, symbol, side, requested/approved quantity, decision/reference and selected-open prices, execution-policy version, and source dataset. This is a conservative rule over OHLCV, **not evidence that Binance rejected a real order or that the order book had no executable liquidity**. It has **zero fills**, zero fee/slippage/turnover, no cash/position/ledger-economic change and no pending order. Persist it as non-economic rejected-intent evidence in the run trace/artifact, explicitly labeled `simulated`; ensure the rejection survives serialization, digests, and comparison output. A missing, negative, NaN/infinite, malformed, or unverified selected bar, or contradictory volume/trade-count fields, remains a **coverage/manifest error**, not a no-fill. If source bars do not carry trade count, zero base volume can support the simulation rule but the artifact must say which field was used.
3. Allow **only that exact broker outcome** to bypass Stage 05's required-fill/achieved-target fatal checks. Do not relax risk rejection, partial fill, broker indeterminate status, mismatched cost/constraints, or nonzero-volume underfill. Keep target selection and `lastRebalance` at the original signal, even if all orders did not fill; the portfolio and metrics reflect actual holdings. At the next *normal* strategy decision, recompute intents from the then-causal data and actual holdings. There is no per-minute retry, carried order, cached quantity, or delayed price. A one-shot buy-and-hold may consequently stay in cash for the whole run; do not silently add an extra entry opportunity. Existing `lastTargets`/cadence behavior must be checked per baseline and candidate so a no-fill neither suppresses an intended future rebalance nor creates a new one.
4. For a risk-stop/mandatory exit, record the same zero-fill rejection, keep the position and its risk/exposure in the portfolio, and allow the next **normal** decision to re-evaluate. This means a transient stop can disappear before the next permitted decision; that is a material economic choice, not a guarantee that the stop eventually executes. Block additions whose shared risk decision cannot accommodate the retained exposure/cash. Do not mark an exit completed or invoke residual-dust reconciliation for a zero fill. Record requested/approved/filled `Q/Q/0`, remaining exposure, reason and concurrent stop reasons in exit evidence. If mandatory stops must remain latched until filled, that requires a separately versioned strategy/position-management change; it is outside this minimal execution-policy change.
5. Retain reductions-before-additions and economic-identity symbol ordering. A failed sell releases no cash or turnover budget; later buys must use actual remaining cash/gross/position slots through shared risk. A failed buy consumes no cash or turnover. Subsequent symbols still run in order, and a no-fill on one symbol does not change another symbol's selected time or price. Frozen target weights are **not redistributed** to survivors. Distinguish attempted from executed turnover and achieved allocation. Do not claim target exposure was achieved when a zero-fill leaves it short.
6. Under `final_policy=liquidate`, a zero-trade selected final exit is a **failed liquidation**: return a structured failure diagnostic containing the simulated rejection, symbol/time/remaining quantity, and do not publish a completed comparison/fold; never call it a completed liquidation or silently use `mark_to_market`. Under `final_policy=mark_to_market`, leave any open position as explicitly marked inventory, with no imaginary exit fill or fee. Existing exchange-minimum dust is a different reason and remains separately labeled. If the research need is to complete liquidate-policy runs despite final no-fill, that is another explicit valuation-policy choice requiring separate metrics and comparability gates.
7. Cash and all comparison lanes share the same execution policy, selected bars, final policy, fee/slippage, exposure limits and timing. Genuine no-fills reduce achieved exposure and may make a candidate/baseline economically unmatched; show both sides' rejected counts, achieved exposure and actual turnover, and let existing comparability gates fail if tolerance is exceeded. Do not normalize away the missed allocation, recalculate baseline at a convenient later price, or present positive nominal return as sufficient. A run with only rejected entries remains `strategy_zero_trades`/non-promotable rather than successful execution.
8. Stage 07 fold primitives count all required chronological market/decision observations, including zero-trade bars and no-fill decisions; no-fill is **not** a coverage hole. Fill/trade primitives contain only real fills with positive available liquidity; rejected intents need a separate digest-bound primitive or linked evidence, never a zero-notional fake fill. Marked residuals reconcile to curve and ledger. Preserve zero-trade/insufficient-trade, exposure/turnover comparability, cohort, and coverage gates; new rejection counts should be visible to review but cannot themselves satisfy trade gates. Validate that the source bridge and immutable experiment manifest carry v3 and rejection evidence, rather than reusing v2 fold artifacts.

## Implementation touchpoints and edge cases after approval

Touch `tradingcore` broker result/rejection metadata only as needed; `internal/backtest/stage05.go` broker construction, no-fill classification, target/exit bookkeeping, final liquidation and artifacts; execution policy default/validation and manifest/comparison normalization; Stage 07 source/primitives/digest readers; operator diagnostics and the Stage 03/05/07 docs and backtest runbook. Keep paper/live adapters unchanged and live submission fenced. Do not encode a generic `CostModel.RejectCode` that rejects all symbols: this outcome is per selected intent/bar and belongs to backtest execution evidence.

Edge tests: archived 04:00 selected entry with 03:59/04:01 traded neighbors (no fill at 04:01); unchanged holding crossing 04:00; later scheduled rebalance on actual cash/positions; one-shot hold remains cash; failed reduction followed by another-symbol buy with no fabricated proceeds; two simultaneous symbols, one zero and one positive, deterministic order and independent outcome; stop-only zero fill and next normal decision; final `liquidate` fails versus `mark_to_market` residual; positive-volume v3 parity with v2; negative/missing/nonfinite volume still fails coverage; risk rejection stays distinct from broker no-fill; no economic ledger/fee/turnover on rejection; repeated runs byte-stable; Stage 07 rejects zero-trade folds and preserves full observation coverage. Use an isolated PostgreSQL 16 schema for integration checks, never the shared test schema.

**Approval choices before changing economics:** (A) accept the one-window zero-fill/cancel outcome and normal-cadence reevaluation, including a possible missed one-shot entry and a non-latched stop; (B) keep `liquidate` strict on a zero-fill final exit while `mark_to_market` reports residual inventory; (C) confirm that no-fill evidence counts as an observation but never a trade or valid fill. If stop exits must be latched or failed final liquidation should complete as marked inventory, specify that separately before implementation.
